Atari Falcon030. For every selected build, the hashed shipped DOS executable
and its observed execution are the behavioural authority; a recovered source
tree is supporting evidence, never a replacement for the DOS oracle:

## 1. Disassembly

**Container before code.** Parse the MZ header and *read the relocation table*
before anything else. F29 has exactly four relocations, all patching one segment
value — which said immediately that the program computes its own segments and is
essentially one 64 KB segment plus a tail. Then read the first thirty
instructions; startup code is short and hands you the memory model. *(F29
`X86DISASSEMBLE.md` §1; UW1 `reassembly.md` §2.)*

✗ **Withdrawn (2026-08-20).** This paragraph used to continue: *"UW1's
relocation table is the opposite lesson: it carries junk entries with pages past
`e_cp`, which crash a stock loader."* There are no junk entries. The claim came
from reading the records as `(page u16, offset u8, pad u8)`; DOS relocations are
`(offset u16, segment u16)`, 4 bytes, target file offset
`e_cparhdr*16 + (segment<<4) + offset`. Re-measured on both UW binaries:
**every** entry valid, unique and inside the mapped image — UW1 3,176/3,176
(`0x320A..0x61546` ⊂ `0x3200..0x66B30`), UW2 2,809/2,809 (`0x2E0A..0x6B08E` ⊂
`0x2E00..0x71B80`) — with the header slack after each table all zero. Two
lessons survive, one of them inverted: **an "invalid" relocation table is
nearly always a wrong stride, not a broken file**, and **a plausible failure
count is not evidence of a defect** — 2,474 "bad" entries out of 3,176 looked
far too systematic to be a decoding error, and that is exactly why the story
survived. The one thing in the table that *can* crash a stock loader is the
**38 relocation entries in frame `0x0000`** (38 in both UW titles) — a
deduction from the table contents, not a measurement: **TBD**, re-run the
stock loader and read the actual trace before rewriting `ghidra.md` §1.

**Three MZ fields that are routinely misread, and what each one costs.** All
three were live in UW1's notes at once; F29's tooling had all three right, which
is why the same family of documents disagreed with itself for months.

| trap | correct | what a wrong reading produces |
|---|---|---|
| `e_ip` @ `0x14`, `e_cs` @ `0x16` | in that order | a wrong entry point that still *looks* like code, plus a paragraph explaining why "the entry lands mid-function" |
| image size | `(e_cp − 1) × 512 + e_cblp` | a phantom gap or tail between the real image end and whatever follows it |
| `e_lfanew` @ `0x3C` | only exists if `e_lfarlc ≥ 0x40` | when `e_lfarlc = 0x3E` the u32 at `0x3C` straddles into the relocation table and reads as a plausible constant, then gets explained away as "linker junk" |

The cheap insurance is the same in every case: compute the entry point, then
disassemble twenty instructions there. A CRT start is unmistakable — for Borland
16-bit it is `mov dx,<DGROUP>; mov [cs:..],dx; mov ah,30h; int 21h; mov bp,[2];
mov bx,[2ch]; mov ds,dx`; for Watcom it is `E9 xx 00` jumping over the embedded
`WATCOM C/C++16 Run-Time system` banner (all three programs of TIE's launcher
chain enter exactly so, and the 32-bit CRT does the same over its own banner —
the "CRT tag" TIE's docs had located *was* the unrecognised entry point). If
what you find needs an excuse, the field is wrong. *(UW1 `reassembly.md` §2;
TIE `DOS4G-header.md`.)*

**Reloc entry 0 hands you DGROUP for free.** In Borland `C0.ASM` output the
first relocation patches the segment immediate of the very first instruction
(`mov dx,<DGROUP>`), so entry 0's target is `entry+1` and the word there is the
static DGROUP segment: `DGROUP file offset = e_cparhdr*16 + (dgroup<<4)`.
Verified on UW1 (`0x5C0F` → `0x5F2F0`), UW2 (`0x6608` → `0x68E80`) and
`UWSOUND.EXE` (`0x0465` → `0x4A50`). The Turbo C copyright banner is the first
thing in DGROUP in all three, so it is a one-line check of any address model —
but the *exact* offset is not constant (UW1 and `UWSOUND.EXE` DGROUP+4, UW2
DGROUP+8, the leading words differ), so search for the string and subtract, do
not assume a displacement.

**Recursive descent is the spine; never linear-sweep.** A linear sweep through
data produces plausible instructions and no way to tell they are wrong. In
16-bit mode two details matter: mask near-branch targets into their segment
(track `(segment, offset)` pairs, not flat addresses, or backwards branches show
up as `0x1xxxx`), and treat only `int 20h` as terminal — `int 21h` usually
returns. *(F29 `X86DISASSEMBLE.md` §2.)*

**Keep a known-data guard, and check it after every run.** Every technique that
widens coverage can be pushed until it manufactures code out of data. F29 keeps
an explicit list of proven-data regions and asserts that no run disassembles
into any of them. This is what set its parameters: seeding every byte-scanned
call target reached 66.2 % coverage and ate six of ten known-data regions;
requiring two independent call sites reached ~45 % and ate none. **The 66 % is
worthless.** Coverage is only meaningful net of the guard — a sweep with no
data guard is not measuring what its percentage claims. *(F29
`X86DISASSEMBLE.md` §6, `RE-WORKFLOW.md`.)*

**Prove table lengths, never eyeball them.** A `mov cl,N` before the bounds
check gives the count outright; a branch to an address makes that address code,
so a table cannot extend past it; the start of a known routine bounds it; and
entries pointing back into the table itself are not entries. *(F29
`X86DISASSEMBLE.md` §4.)*

**Byte-scan to break reachability circles.** When a routine is orphaned, scan
raw bytes for `call rel16` targeting it. The scan must run over **raw bytes, not
over discovered call sites** — the routines worth finding are exactly the ones
descent has not reached, so grouping what it did find is circular. *(F29
`X86DISASSEMBLE.md` §3–4.)*

**Call graph beats anchor hunting.** Looking for F29's game loop by searching
for a trig table or a distinctive constant failed twice — both candidates were
data. The call graph found it structurally in one step: highest fan-out in the
largest code region. The trap: attribute call sites to an owner by
*contiguously reached instructions* — a gap ends the routine. "Nearest call
target at or below the site" lets the last routine before a large unreached
region collect every site inside it, producing phantom master-dispatchers (F29's
edge count dropped 607 → 351 once bounded properly). *(F29
`X86DISASSEMBLE.md` §7.)*

**Ghidra 12.1.3 + GhidraDosToolbox handles 16-bit real mode headlessly.** UW1
runs a full import + auto-analysis + C export pipeline: the extension adds the
`x86:LE:16:Real Mode` language, an experimental MZ loader, and a
`DosSyscallAnalyzer` that names `INT 21h`/`INT 10h` calls. Three loader patches
were needed (an out-of-range segment filter — needed for the frame-`0x0000`
relocations above, *not* for junk entries; a `CODE_TAIL` block covering the
unmapped tail, which is the `FBOV` overlay pool rather than a self-load; a
`getStart()` cast fix) and are documented with a `javac`-only rebuild
recipe — no gradle. Flags that actually work in 12.1.3: `-processor` takes the
*language ID*, `-loader` is broken, PyGhidra is not started by `analyzeHeadless`
so post-scripts must be Java. *(UW1 `ghidra.md`.)*

**The syscall-naming payoff is grep.** Once `DosSyscallAnalyzer` has run you can
grep the disassembly for `DosCreateFile`/`DosRead`/`DosSeek` to find the I/O core
instead of reading raw `int 21` sequences. *(UW1 `ghidra.md` §5.)*

**A tail past `e_cp` is a question, not a fact — check for `FBOV` first.** Both
UW1 and UW2 carry a large region that the DOS loader does not map (UW1: 141 KB
past file 0x66B30; UW2: 210 KB past 0x71B80), and both projects assumed for
months that the program self-loads it contiguously at run time. It does not.
The first four bytes are `FBOV`, Borland's **overlay pool** magic:

```
66B30: 46 42 4f 56 | 10 27 02 00 | 60 d8 05 00 | 9f 00 00 00
       "FBOV"        ovrsize       exeinfo       segnum
```

with `ovrsize == pool payload` (the bytes after the 16-byte header) exactly —
check that and the reading is certain. The manager's `Runtime overlay error`
string is in both binaries. Consequences:

- **There is no single tail→memory mapping to find.** Overlays are swapped into
  a buffer, so the same file bytes appear at different addresses at different
  times — UW1 caught two overlays live at deltas `-0xBCA1` and `-0x8F50`.
- A runtime address inside the pool will still "resolve" to a pool function
  name, because the functions tile the region densely. That is not evidence;
  match the *bytes* at CS:IP back into the file instead.
- Reassembly must reproduce the pool, its unit count and every thunk site.

**`segnum` is not the overlay count, and `exeinfo` is the map.** Both projects
misread `segnum` for months (UW1 "159 overlay segments", UW2 "174"). It is the
row count of the segment table at `exeinfo`, which describes **every** linker
segment as `{u16 seg, u16 size_bytes, u16 type, u16 flags}`, chained by
`seg + size_bytes/16`; the DOS loader relocates the `seg` column, so a RAM dump
shows every row shifted by the load segment and nothing else. **`type == 3`
marks the overlaid segments**, and each of those is a *stub*: a 32-byte header
followed by its 5-byte `INT 3Fh` thunks.

    +0x04 u32 pool offset (relative to the pool's code start; the manager
              turns it into a file offset at load time)
    +0x08 u16 code size      +0x0A u16 fixup size    +0x0C u16 entry count
    +0x10 u16 resident segment, 0 = not loaded   (runtime)

That is the **same header shape Turbo Pascal's `TPOV` uses** (below) — one
parser covers both families. Four checks make it self-proving, and all four
pass on UW1 and UW2:

| | UW1 | UW2 |
|---|---|---|
| segment-table rows / overlaid (`type 3`) | 159 / **64** | 174 / **77** |
| `0x20 + 5*nent == stub size` violations | 0 of 64 | 0 of 77 |
| thunks (`CD 3F` + u16 entry offset + `00`), operand ≥ unit code size | 602 / **0** | 928 / **0** |
| `CD 3F` sites = stubs + thunks + 1 (the installer's vector byte) | 667 = 64+602+1 | 1,006 = 77+928+1 |

The units tile the pool in table order, paragraph-aligned, ending within a
paragraph of EOF. Tool: UW1's `work/overlay_map.py`.

**The dispatch is self-modifying, so don't hunt for a dispatch table.** UW1's
handler was expected to end in a `call far dword ptr ds:[0x26]` into the
freshly loaded unit; that slot is never patched and points at a `retf` — a
no-op hook. What the manager actually does is **overwrite the 5-byte thunk in
place with `EA <off> <seg>`** (a far jump into the resident copy) and back the
saved `IP` up by 2 (`sub word [bp+2],2`) so the `IRET` re-executes it. First
call pays the interrupt, every later call is a direct jump. A RAM dump proves
it and hands you the map for free: UW1's showed 70 of 602 thunks patched, each
target landing on a `55 8B EC` prologue. It is also why the record is 5 bytes.

*(UW1 `uwexe.md` §13.6, measured on the running game 2026-08-23; the same
parse verified in-file against UW2.)*

**Turbo Pascal's scheme is the same opcode with a static map.** POR's overlay
lives in a separate file (`GAME.OVR`, `TPOV` magic) and each unit keeps a
resident header in the EXE — `u32 fileOffset, u16 codeSize, u16 fixupSize,
u16 entryCount` plus 5-byte `INT 3Fh` entry thunks. The directory chain
`fileOffset + codeSize + fixupSize == fileOffset(next)` is exact over all 38
units and every one of the file's 232,379 bytes, and resolving the thunks
yields **774 real entry points** — the list that makes everything after it
tractable. Two consequences for any `INT 3Fh` program, Borland or TP:

- **`INT 3Fh` is not an instruction boundary.** The thunk is `CD 3F` plus 3
  descriptor bytes; decoding those as opcodes derails a descent instantly —
  POR's first walk reported "33 × int 3Fh" and 0 % coverage, all of it
  garbage. Step over 5 bytes and continue.
- **Decompile per unit, not per file.** Import each overlay unit (or pool
  segment) as its own raw image at `0000:0000`, with its entry list seeded in
  a *pre*-script — a raw binary has no entry point and auto-analysis finds
  almost nothing unaided. The decompiler's addresses then equal your unit
  offsets, and the densely-tiled-pool false-resolution hazard (§7) cannot
  arise. POR: 758 seeds became 1,102 functions across 38 units, seconds per
  unit headless.

*(METHOD.md §2.2–2.3, §3.1; POR `analysis/executables.md`.)*

**A DOS/4G game is an MZ stub plus a standard `LE` module — parse it as one
before inventing a private header.** The LE object table, object page map and
fixup tables partition the file with self-checking arithmetic:
`data_pages_off + (pages−1)*page_size + bytes_on_last_page == filesize`, and
the fixup page table's last entry lands exactly on the import module table.
TIE's docs carried a plausible "DOS4G-OLX private header" model for five days
— vector tables, selector tables, 9/11-byte thunk records, a 16-bit half —
every field of which an assumption-free parse collapsed into the standard LE
map: the "selector table" is the object page map, the "thunk records" are
tails of ordinary fixup records, the "16-bit half" beyond the MZ stub does not
exist. The fixup table then doubles as a **reverse-xref index**
(`work/audit_fixups.py --target=OBJ:OFF`) — the only xref mechanism that can
work on an LE image, because raw operands are stored object-relative and
patched at load time (§3). *(TIE `work/audit_headers.py` /
`audit_fixups.py`; absorbed into the analysis docs 2026-08-21 —
`DOS4G-header.md` quotes each withdrawn reading beside its LE reality. The
same audit caught a second instance in the same repo: `TIE.EXE`'s "8-entry
pointer table @ 0x20" was its MZ relocation table, and its "e_lfanew 0x39EC"
was relocation data — with `e_lfarlc = 0x20` the table starts *before* 0x3C.)*

## 2. Idioms that derail a disassembler

These are properties of *hand-written* real-mode code. Compiler output (UW1/UW2
Borland, TIE Watcom, POR Turbo Pascal) mostly does not do them — but "mostly"
is why it is worth checking rather than assuming.

**Inline data after `call`.** `call print_routine` followed by the string bytes
in the instruction stream; the routine does `pop si` to take the return address
as the pointer and `jmp si` past it. Anyone unaware disassembles into the text
and loses everything downstream. Detect by scanning raw bytes for `call rel16`,
grouping by target, and classifying a target as an inline-string routine when it
has ≥3 call sites with text following at ≥80 % of them; then iterate to a
fixpoint. Terminators vary — F29 uses "byte with bit 7 set", which also means a
naive `strings` dump corrupts the last character of every string (`SCENARI`,
`FIRE AND FORGE`). **If your strings look like they are missing their last
letter, this is why.** The same idiom appears for inline jump tables and inline
hardware init sequences. *(F29 `X86DISASSEMBLE.md` §3.)*

**Self-modifying immediates as the standard way of holding state.** F29 stores
airspeed, altitude, pitch, bank and heading in the immediate of the instruction
that reads them — on an 8086 `mov ax,imm` beats `mov ax,[mem]` because the
immediate is already in the prefetch queue, so it is an optimisation, not
obfuscation. The diagnostic: **when an address has writers and readers but no
consumer that does anything with the value, check whether the address itself
lands inside an instruction.** Conversely, before trusting a table, scan for
every `mov [imm16],reg` targeting its range; finding none is worth knowing.
*(F29 `X86DISASSEMBLE.md` §5.)*

**Jumps into the middle of an instruction.** An F29 decompressor emits a literal
escape byte by jumping to the second byte of `cmp ax,0xC38A` (`3d 8a c3`),
executing `8a c3` = `mov al,bl`. The disassembler shows one instruction; two
exist.

**Signed vs unsigned comparisons.** `cmp al,0x41 / jl` is *signed*, so values
from `0x80` up take the low branch too. Reading it as unsigned sent F29 hunting
for a second dispatch table that does not exist. When a dispatcher seems to have
a hole, check the condition code.

**Packed data read as unpacked.** F29's overlay dispatch table gave nonsense
until the *decompressed* resource was read instead of the stored one. What hid
it: the packed stream happened to begin with bytes containing no escape byte, so
the first entries decoded perfectly. **If a structure is valid at the start and
garbage further in, suspect compression.**

## 3. When cross-references come back empty

Three projects have hit "I searched the whole image for a reference
to this address and found none", and in **every case the data was fine and the
address model was wrong**:

- **TIE**: no reference to a known string (`img+0x0A98BF`) exists as a 32-bit
  immediate *or* a 24-bit image-relative value under any base tried. The
  operands in the raw file are unrelocated — the DOS4G/LE loader patches them
  from fixup records at load time. Immediate-scanning simply cannot work on
  that image until the fixups are applied. *(TIE `ztie.md` open question 9 —
  since answered statically by decoding the fixup table itself, §1:
  `audit_fixups.py --target=2:0xBF` returns the single source site of the
  CD-check string.)*
- **UW1**: 111,801 instructions scanned, **zero** direct references into the
  string pool at file `0x5F000..0x61700`, and no u32 far-pointer table. The
  strings are resolved at runtime (STRINGS.PAK ids or separate seg/off
  immediates). *(UW1 `uwexe.md` §10, `functions.md`.)*
- **F29**: an address with writers and readers but no consumer turned out to be
  *inside an instruction* (see §2).

**Rule: an empty xref scan is a statement about your reference mechanism, not
about the data.** Before concluding anything, verify the address model end to
end with a worked example — take one known string, compute its address under
your mapping, and confirm the bytes there are that string. TIE's `ztie.md` §4
does exactly this ("Worked check: `img+0x0A981A` = file 0xE881A = … ✓") and it is
the cheapest insurance in the whole workflow.

## 4. Proving a decode rather than guessing it

In increasing order of strength:

1. **Plausible disassembly** — the weakest evidence available. Every wrong
   finding logged in F29's `RE-NOTES.md` passed a plausibility check first.
2. **Round numbers that fall out exactly.** An F29 decompressor correction
   turned ten outputs into *exactly* 32,000 bytes = 320 × 200 × 4 bits. Both
   archive index tables end with a sentinel equal to the file size and the
   resource lengths sum to the file exactly.
3. **Structural invariants that must land.** All 74 F29 music patterns tokenise
   to end precisely on a boundary derived independently from the sequence table
   — one wrong operand size anywhere would desynchronise. That single fact
   validates 27 opcode definitions.
4. **Independent derivations agreeing** — three HUD fields all resolving to the
   same `frame_count`.
5. **Simulation** — run a suspected PRNG and check its period and distribution.
6. **Render it.** For anything visual, convert and look. A recognisable title
   screen or control tower ends the argument in a way no byte-level reasoning
   does.
7. **Run it.** With the DOS oracle (§6) the original is now observable directly.
8. **Rebuild it.** Reassemble your disassembly and diff against the original.
   A SHA-256 match over the whole file is not evidence *about* one decode, it is
   simultaneous confirmation of every byte: entry point, every instruction
   boundary, the relocation format, the segment layout, the container arithmetic.
   Nothing else in this list is that comprehensive. UW1 does it in 25 s (§4a).

**Keep storage geometry separate from display geometry.** A resource header may
carry a visible mode, a stored pitch/maxima, an allocation capacity, and a
palette or other tail at different boundaries. Derive the decoded extent and
termination from the original consumer's read loop plus corpus invariants;
record stored width/height, visible viewport, capacity, and tail separately.
Comanche's `CONSOL1S.DTA` caught this: its header says 320x200 for the VGA
display, but the consumer decodes a 328x290, 95,120-byte surface before a
separate 769-byte palette tail.

**Statistics separate code from data cheaply.** Opcode frequency: `call` at
1.9 % and `ret` at 1.0 % in real F29 program text against 0.29 % and 0.15 % in
the archives — an order of magnitude, enough to settle whether a file contains
code at all.

## 4a. Byte-exact reassembly as a harness

UW1 rebuilds all 561,744 bytes of `UW.EXE` from generated NASM source to the same
SHA-256 — header, relocation table, load module and Borland `FBOV` overlay pool
(`UW1 reassembly.md`). The technique is game-independent and the design decisions
are what make it work:

- **Guarantee exactness by construction, then measure quality separately.**
  Every instruction is rendered as text, assembled, and its bytes compared with
  the original. Anything that does not match falls back to `db` with the mnemonic
  in a comment. Because the fallback always matches, the file is byte-exact from
  the first working run; the only thing left to improve is the *percentage* of
  real mnemonics (UW1: 99.98 %, 26 `db` out of 163,030). Do not try to get the
  encoder perfect first — you will never finish, and you cannot tell how close
  you are.
- **Compare per line at the line's *intended* offset**, not at the offset the
  assembler happened to emit. One instruction assembling one byte short shifts
  everything after it; comparing against intended offsets keeps the report
  pointing at the single real culprit instead of 100,000 innocents.
- **Emit branch targets `$`-relative** (`jmp short $+2+N`). The encoding then
  contains no absolute address, so a flat `nasm -f bin` rebuild of a *segmented*
  real-mode program is exact and 64 KB wraparound cannot corrupt anything.
- **Derive operand-size qualifiers from the original encoding**, don't search for
  them. capstone's `encoding.disp_size` / `imm_size` / `modrm` say which form the
  original used, so `[word bx+8]`, `[byte bx]`, `byte 0x10` are computed.
- **Compilers pick encodings assemblers won't.** Borland emits register-register
  ALU/MOV with the direction bit set (`8b ec` for `mov bp,sp`); NASM always picks
  `89 e5`. Same instruction, different bytes, and no assembler syntax selects it
  — 7.6 % of UW1's code. Generated macros that build the ModRM byte by hand
  (`%macro mov_rr 2 / db 0x8b, 0xc0 | ((rn_ %+ %1) << 3) | (rn_ %+ %2)`) keep
  those readable instead of dumping them to `db`.
- **Keep both the per-line check and the whole-file compare.** A shadowed loop
  variable once truncated UW1's output by 140 KB while every emitted line was
  individually correct. Only the whole-file hash caught it.
- **The fallback list is a finding generator.** UW1's leftovers clustered on a
  0x100 stride, which turned out to be a 16 × 256 palette shading table
  (`0x109DE`, row 0 the exact identity map, row 15 all zero) that Ghidra had
  claimed functions inside. Whatever will not re-encode is either an assembler
  limitation or data you mislabelled — both worth knowing.
- **Then prove it is a source and not a copy.** Change one string in the
  generated assembly, rebuild, and check the diff is exactly the bytes you
  changed and nothing else.

POR ran the same ratchet independently over its 38 Turbo Pascal units
(`make reasm`: `GAME.OVR` and `START.EXE` both rebuild byte-identical, 80 % of
overlay code as real instructions) and contributes two rules. **Verify per
instruction, never by diffing the whole binary**: its first ratchet demoted
"everything after the last label" on any mismatch and reported a byte-exact
rebuild at 1 % real instructions — technically passing, actually meaningless.
And **rebuild the files, not just the code images** — headers, directories,
fixup blocks; POR's rebuild failing with `unit 016 starts at 0, directory says
4` is how the `TPOV` signature got proven rather than assumed. One definition
to fix in advance: "byte-identical" means identical to the *file* image — a
self-modifying program (F29 keeps live state in instruction immediates) still
rebuilds exactly, its SMC sites simply stay `db`: expected residue, not
failure. *(METHOD.md §2.4; F29 `docs/X86DISASSEMBLE.md` §5.)*

## 5. Bookkeeping that pays for itself

**Keep resolved indirect targets in a file, with the evidence.** F29's
`re/seeds.txt` holds every resolved indirect jump together with the reasoning
that fixed its table length; the disassembler reads it automatically, so coverage
never regresses and nobody re-derives the same table twice. Decode the raw bytes
at a target independently *before* seeding it. The same file stores
**rejections as comments** — an audited-and-refused seed stays visible so
nobody re-adds it without cause: a worklist says where to work, anti-seeds say
where not to. *(F29 `X86DISASSEMBLE.md` §7.)*

**Rename only from a verified anchor.** UW1 commits a rename only when there is
a concrete anchor — an `INT n`/AH immediate at a known file offset, or the MZ
entry point. Everything else stays `FUN_*` for the next pass. Applied renames
live in `work/renames.csv` and are re-applied by an idempotent script that
reports `APPLIED 20/20`, so the analysis database and the exported artifacts
cannot drift apart. *(UW1 `functions.md`.)*

**State the address mapping once, in a table, with a worked check.** Every
project needs `file ↔ runtime ↔ tool-of-the-day` and every project has been
bitten by getting it wrong. *(TIE `ztie.md` §4; UW1 `ghidra.md` §3.)*

**Mark status explicitly** — `RESOLVED` / `PARTIALLY RESOLVED` / `IDENTIFIED` /
`TBD` — and record the verification scope with it (which files, how many
checked). *(TIE convention.)*

**Record corrections in place, with the old wrong reading quoted — and say why
it looked right.** F29's `RE-NOTES.md` withdraws a 36,096 B buffer-size claim
by quoting it, re-measuring, and then naming what always contradicted it and
nobody noticed. A silently-fixed doc teaches nobody why the first reading
looked right. (TIE's 9→11-byte thunk-record correction, once the exemplar
here, turned out to be wrong twice over — both readings were tails of LE fixup
records, §1; the convention survives its example, because the second
correction is recorded the same way.) If a doc is generated or mirrored,
**flag when a fix has not yet reached the upstream copy** — otherwise the next
regeneration reinstates the error. This file has done exactly that once.

**Treat a parallel worker's output as a claim, not a result.** F29 merged an
independent worktree's findings by (1) re-running the tool *in that worktree*
to verify the metric mechanically, (2) spot-checking the two most
valuable-looking findings against independent prior work, then (3) auditing
everything else address by address from raw bytes. Roughly half was rejected —
including a seed that the source material's own prose, in another section,
called data. Net 45.7 % → 51.8 %, every point re-verified rather than
imported; the rejections went into `seeds.txt` as comments. *(F29 commit
`717ab60`.)*

**Record dead ends.** Two F29 documents exist mainly to say what something is
*not*. That is worth as much as a positive result to whoever comes next.

**List the regeneration command for every derived artifact.** *(TIE `work/README.md`
convention.)*

## 6. Dynamic analysis: the DOS oracle

The twelve reverse-engineering siblings carry an identical harness that
boots genuine MS-DOS 6.22 in QEMU and runs the original game headless; POR also
runs the complementary DOSBox-X half (below), and CMN a third route — the
game's *own* screenshot writer under DOSBox, with the developer-key gate
patched out (`CMN tools/oracle-capture.sh`). WC1 is the one member still
without it. Shared verbatim: `dosimg.py`, `run_qemu.py`, `mbr.asm`,
`gdbstub_probe.py` — **master copies in `../F030Method/dos/`**: fix
there (or copy a project-local fix back there first), then
`python dos/sync.py --push` updates every project, and plain `sync.py`
reports drift. Per-game and never synced: `build_dos_hdd.py`,
`set_boot_mode.py`. Each project's own `qemu-boot.md` / `DOS-ORACLE.md` has
the details.

`sync.py` compares the copies a project *has*; a project that never seeded the
harness has no copy to drift, so it reports clean by having nothing. Read the
`absent` lines at the end of its output, not just the exit status — that hole
is how CMN's missing oracle stayed invisible while METHOD.md §4.2 was citing
CMN's terrain gap as the case only an oracle can close.

**The thing that actually stalls a seeding is the prerequisite, not the code.**
The harness needs the genuine MS-DOS 6.22 install floppies — mformat's own boot
record hangs in QEMU, so a real one is required — and that set was acquired per
project: UW1 and TIE each carry a byte-identical 5 MB `.7z`, UW2 a third
extracted copy, POR reaches into UW1's directory by a hardcoded path, and F29
pointed at an `img/` it does not have. `dosimg.find_floppies()` now resolves it
the way `host_tool()` resolves programs — `$DOS622`, this project's `img/`, any
sibling's `img/`, or a `.7z` in any of them expanded once — using a sibling's
copy *in place* rather than duplicating it. `sync.py --init` writes a working
`build_dos_hdd.py` skeleton too, because "copy a sibling's and adapt it" was
the step where seeding stopped. CMN went from `absent` to a booting image and a
driven capture of the running game in one sitting on that basis.

Why it matters for reverse engineering: questions that static analysis cannot
settle — a self-loaded tail's runtime base, a segment/pool base register, which
branch a dispatcher actually takes, whether a decoded format is right — are one
boot away. UW1's remaining open questions are explicitly of this kind.

Three techniques inside it generalise beyond DOS:

- **Let the guest end the run.** An 8-byte `QUIT.COM` writes to QEMU's
  `isa-debug-exit` port, so QEMU exits with a distinctive code (21) when the
  work is done. Any other exit means a hang or crash — no timeout guessing.
- **Assert invariants at build time, not debug time.** The image builder
  asserts five boot-record invariants; a violation fails the build with a clear
  message instead of producing a disk that silently does not boot. Every one of
  those five was a real multi-hour failure first.
- **Observe through whatever channel actually works.** The Windows QEMU build's
  serial sink is a no-op (TIE accumulated 22 empty `serial*.log` files before
  this was believed). What works: files the guest writes, read back with mtools;
  QMP `screendump`; and `pmemsave 0xB8000` decoded as 80×25 text.

**DOSBox-X is the complementary oracle** (POR `analysis/dos-oracle.md`): its
`[log]` section takes per-category switches — `int10`, `io`, `vga`, `int21`,
`fileio` — and a dummy SDL video driver runs it headless, which is I/O tracing
QEMU cannot match for cheapness. Two POR lessons come with it: plain `timeout`
is not enough (DOSBox-X survived SIGTERM; use `-k`), and **an absence in a log
is evidence only if the run demonstrably reached the code that would have
written the entry** — POR's zero `INT 10h`/port-write counts turned out to
mean "the game never got past its startup check", not "the game never
programs a palette". Prove the code path was reached; then trust the absence.

### Address vocabulary, dumps and unpacking

Keep four address spaces separate: DOS `seg:off`, guest physical, guest linear,
and file offset. In real mode the usual physical/linear calculation is
`(seg << 4) + off`, subject to A20 and wrap rules; the same byte can therefore
have many valid segment:offset spellings. In protected mode a selector is an
index into the GDT/LDT, not a flat segment base, and a DOS extender's selector
and DPMI state must be recorded before translating an address. Neither value
is a file offset, and none is automatically a Ghidra address.

QEMU's monitor uses `x` for virtual-memory examination and `xp` for physical
memory. `pmemsave` also saves physical memory. Thus
`pmemsave 0 0xA0000 ram.bin` covers conventional addresses `0x00000..0x9FFFF`;
it does **not** include the VGA aperture at `0xA0000`. Dump that aperture
separately, for example `pmemsave 0xA0000 0x20000 vga-aperture.bin`, and keep
VGA registers and palette state as separate evidence. The IVT is at physical
address zero; protected-mode runs additionally need the IDT, GDT/LDT and DPMI
state.

`-d in_asm,exec` is useful for locating executed translation blocks, but it is
not an unpacked-image dump and not a stable per-byte coverage format. A stub
that reaches a decoded entry proves that the path ran; it does not preserve the
decoded bytes. Schedule a RAM dump or capture memory writes at the transition,
then validate the captured bytes against the runtime address map. The shared
TCG plugin in `dos/trace/` is the authoritative telemetry path here. A `drcov`
export is optional visualization glue only: rebase it to the analyzed image
and retain scenario, overlay-unit and file-offset identity, because two overlay
units can occupy one address at different times.

QEMU's GDB stub can be used with Ghidra or IDA, and Ghidra has explicit 16-bit
real/protected-mode processor languages, but a remote session does not infer
segment bases, loader mappings, compiler conventions or trustworthy C types.
Use it to stop, inspect and correlate; keep the measured DOS oracle and the
file/runtime mapping authoritative. DOSBox-X's debugger is the complementary
interactive DOS tool. Hardware emulators such as 86Box are a timing or device
compatibility fallback, not a replacement for the reproducible QEMU oracle.

### Probing the running game (`gdbstub_probe.py`)

Booting is half of it; reading the running program is the other half. The shared
probe does that over **QMP `human-monitor-command`** — QEMU's raw gdbstub was
tried first and drops commands intermittently on this Windows build. It is
game-agnostic: it finds the project root, the image (via the `.geom.json`
sidecar), the largest MZ binary in the game tree, the Ghidra skew (from
`e_cparhdr`) and the overlay pool (from `FBOV`) by itself. Pass `--exe` when the
heuristic picks the wrong binary — in TIE it finds the installer-compressed
`Z_TIE__.EXE`.

What it does, and the lesson behind each:

- **Calibrate `file → linear` from signatures in RAM.** Several candidate
  16-byte windows, not one: a window that looks fine statically can have been
  overwritten by the time you look, and a single auto-picked window did exactly
  that on the first attempt. Skip windows containing a **relocation** (parse the
  MZ reloc table) — the loader has patched those bytes — and take a majority
  vote. UW1: 6 of 8 agree on `+0x2760`, giving load segment 0x0596.
- **A 16-byte match proves 16 bytes.** Then check the *whole* file against RAM,
  16 B every 4 KB. This is the step that overturned UW1's tail model: 1 of 35
  windows of the "self-loaded tail" was resident, the rest zeros. Expect
  ~70–75 % matches in the mapped image; the misses are applied relocations, and
  seeing `push 0x55E1` in the file as `push 0x5B77` in RAM (`0x55E1 + 0x596`) is
  a free confirmation of the load segment.
- **The hottest address is probably an interrupt handler.** UW1's EIP histogram
  is dominated in every game state by a 16-slot timer dispatcher at file
  0x24A2A that Ghidra never disassembled — it is reachable only through a vector
  installed at run time. `SS == CS` with a small `SP` is the tell. Exclude it
  before drawing conclusions about "the game loop".
- **Drive the game with `sendkey`, and screenshot every step.** UW1: 3× `esc`
  walks title → intro → main menu, and the 4th quits to DOS, so `QUIT.COM` ends
  the run and the monitor socket closing mid-probe is a *normal* outcome. Without
  a screenshot per step you cannot say which state a histogram measured.

**A wrong result from a check is sometimes a measurement bug, not a code bug.**
An F29 frame grabbed too early shows the TOS desktop, not the program; a frame
rate divided by the wrong interval gives a plausible but meaningless number.
Before changing code because a check came back wrong, confirm the check measures
what it claims to. *(F29 `RE-WORKFLOW.md` Traps.)*

## 7. Traps that cost real time

- **Reading rendered digits at thumbnail scale.** F29's debug font is 4×5
  pixels; screenshots produced real misreadings — "913" for "013", "12352" for
  "12952" — that looked exactly like plausible bugs. Crop and upscale before
  debugging a discrepancy that involves reading rendered text.
- **`open(p,'w')` truncates immediately.** When editing a doc from Python, build
  the whole string first, then open for writing, and specify UTF-8 explicitly. A
  `UnicodeEncodeError` raised after the open leaves an empty file, and a
  following `git add -A` commits the loss. This destroyed F29's `RE-NOTES.md`
  once.
- **Python stdout is block-buffered when redirected.** Run long tools with
  `python -u`, or a hang leaves you an empty log and no idea where it stopped.
- **A tool that disagrees with the authoritative listing is wrong.** F29's
  `peek.py` has reported misaligned addresses more than once; the
  recursive-descent listing wins.
- **`mtype`/`mcat` on a missing file dump the raw image** and look like content.
  Always check the exit status. *(TIE.)*
- **7-Zip reads FAT12 floppy images and LZH directly, but not ARC — and it does
  not fail loudly.** `7zz x` on an ARC reports success with `Files: 0`, so a
  script that ignores exit codes silently produces an empty tree. Use
  `unar`/`lsar` and verify against the archive's stored CRCs. *(POR
  `analysis/tools.md`.)*

### Flags and offsets that silently change the answer

The expensive bugs in this project family are not crashes. They are settings
that produce a *well-formed, plausible, wrong* result, which then gets written
into a doc and believed. Several of these were live at once in UW1:

- **`ndisasm -u` is a synonym for `-b 32`** and silently overrides an earlier
  `-b 16`. A 16-bit program decoded as 32-bit yields real-looking instructions:
  `cmp al,[ss:bx+di]` becomes `cmp al,[ss:ecx]`, and a `call far` swallows the
  next instruction. UW1's "the string pool is at segment 0x19A0" finding came
  from exactly this and survived in the docs until the boot trace contradicted
  it. Use `ndisasm -b 16 -o <linear>` and nothing else. Related: with an origin
  above 64 KB, branch targets print truncated to 16 bits.
- **Ghidra's image base is not `0x10000 + file offset`.** The MZ *header* is not
  mapped, so the skew is `0x10000 - e_cparhdr*16` (UW1 0xCE00, UW2 0xD200, F29
  0xFE00). The obvious formula is wrong by the header size and names every
  address with a real function that is simply the wrong one. Derive the skew
  from the header and check it against a known string before trusting a name.
- **A name that resolves is not evidence.** Densely tiled function tables (an
  overlay pool, an auto-analysed blob) return a plausible `FUN_xxx+0y` for any
  address you hand them, including addresses that are not in that region at all.
- **`mcopy -o` only covers clashes on the DOS side.** Overwriting an existing
  *host* file needs `-n`; without it a rebuild over a populated staging
  directory stops on `File "./IO.SYS" exists, overwrite (y/n) ?` and blocks
  forever on a tty that does not exist. Fixed in the shared `dosimg.py`.
- **`mmd` does not create intermediate directories.** When staging a tree,
  schedule every ancestor (`CARS` before `CARS/CARS93`), even if no file lives
  directly in the intermediate directory. ICR exposed this when its first
  image build failed on the nested car-data path; the shared `dosimg.py` now
  expands directory prefixes before issuing `mmd`.
- **QEMU prints `ES =1234`, with a space before the `=`**, and calls the flags
  register `EFL`. Parsing `info registers` by splitting on whitespace and
  requiring `=` in the token silently drops *every segment register* and reports
  `CS=DS=ES=SS=0000`; every linear address computed from that is then wrong, and
  looks merely odd rather than obviously broken.

## 8. Porting: the phase playbook

The port side of this family lives in `../F030Method/METHOD.md` — read
it in full when a project crosses from analysis to implementation. The
load-bearing policies, so their names are known here:

- **Four phases, in order, per vertical slice**: decode → disassemble + prove →
  understand → port. A byte-exact source-file rebuild is a powerful
  reconstruction invariant where available, but it does not by itself prove
  code classification or semantics; keep independent entry-point evidence,
  data guards, residue classes and runtime witnesses.
- **Fidelity is an observable contract.** Preserve rules, ordering, arithmetic
  widths and results over the declared supported scope while adapting hardware
  mechanisms at explicit seams. A claim of 100 % fidelity is a conclusion from
  the comparison chain, never an implementation intention.
- **Nothing without a source**, which is a rule about code and not only
  about data: **never write 68k code without referring to a DOS routine.**
  Every ported routine header names the hashed source image, canonical range,
  behavioural contract and classification evidence grade; code that cannot do
  so is left stopped or dormant. Every non-trivial item is explicitly one of:
  **Grounded** (cites that authority), **Target artefact**
  (serves the Falcon, claims nothing about the original), or **Unproven**
  (loudly marked at the definition, listed as an open risk). An unproven item
  may not be used to justify a second assumption. Keep every legitimate DOS,
  BIOS and hardware substitution in one closed, project-local list and review
  that list as a whole whenever it changes.
- **m68k output is assembled and measured, never guessed.** `m68k` is a family,
  not a target declaration: every 68000-side routine records the exact CPU
  (MC68000/020/030/etc.), assembler or compiler and version, syntax, ABI,
  calling convention, memory/alignment and privilege assumptions, and output
  format. The declared toolchain must be configured for that CPU and must fail
  unsupported instructions/addressing modes. Retain the source, build command
  or configuration, object/binary hash, and assembler/compiler listing or
  disassembly. Before the routine is called a target counterpart, run its
  contract fixtures in the declared 68k emulator or on the Falcon target and
  compare canonical outputs and side effects. A hand-written snippet that has
  not passed these gates is `Illustrative`, not `Ported` or `Verified`; a
  passing JavaScript fixture proves behavior at the contract boundary, not
  m68k instruction legality or execution. Shared code targets the lowest
  declared CPU; CPU-specific extensions belong in the target seam with their
  fallback boundary recorded.
- **The DOS binary is the behavioural authority; the complete function
  inventory is preserved.** Every recovered DOS function remains in the
  project's durable inventory, whether it is implemented in the browser,
  68000, both, or neither yet. `Identified`, `Unproven`, `Ported`, `Verified`
  and explicit out-of-scope statuses are acceptable; silently dropping a
  function or replacing it without a record is not. For every function that
  enters the browser or target path, maintain its hashed DOS identity,
  recovered contract, fixtures, implementation symbols and a difference
  ledger against DOS. State and prove even “no difference”; unresolved
  differences are `Unproven`. A recovered source tree, decompiler result or
  reassembly is supporting evidence and must never overrule the selected DOS
  executable.
- **Link implementation source to the disassembled function.** Every
  JavaScript/browser and 68000/m68k function source that implements or exposes
  a recovered DOS function carries an adjacent comment or docstring linking to
  the durable function record and naming the disassembled DOS function symbol
  plus canonical range/entry. Use the same stable function ID in the record and
  both implementation sources; a separate map or file-level comment is not
  enough. Code with no DOS counterpart says `N/A - platform replacement` or
  `Target artefact` at the definition.
- **A deterministic, playable browser/JavaScript game runtime is mandatory.**
  Start it with the first ported function and land its fixtures before or with
  every supported Falcon slice. The browser page itself is the game/reference
  runtime: it boots the DOS-derived data boundary, runs the deterministic game
  loop, accepts input and presents the logical framebuffer, events and audio
  model. A diagnostic asset viewer or isolated canvas demo may accompany it but
  cannot satisfy this rule. It is the day-to-day differential laboratory, not a
  replacement for DOS capture or real-target validation; Canvas output is
  diagnostic, while raw/canonical state, event and framebuffer fixtures are the
  oracle. Use its controllable experiments to identify a function's role,
  contract, state effects and target seam, but promote a finding only after DOS
  evidence supports it.
- **The browser port must be connected game flow, not a test-page collection.**
  Every function marked supported must be wired into the same browser runtime
  with all earlier supported functions. The page must boot without a
  developer-only harness, accept its declared input path and reach the game's
  real startup flow — at minimum the main menu or a deterministic attract-mode
  loop, whichever the DOS build exposes first. Record ordered ticks/inputs,
  state checkpoints, logical framebuffer/page hashes and emitted events for that
  flow. An isolated function may remain `Identified` or `Unproven`, but it is not
  part of the supported browser port until this connected-flow gate passes.
- **Input must run through the DOS I/O driver and must not improve game flow.**
  Physical/browser keyboard and pointing-device events are transport data only:
  feed them into the recovered DOS driver contract, then run the authoritative
  DOS consumer and preserve its widths, units, transitions, queues, polling,
  acknowledgement, ordering and error results. A DOM click or key may not call
  a selection helper, inject state, synthesize an action or bypass an unported
  function. An unrecovered keyboard path remains `Unproven`; convenience
  shortcuts are labelled test controls and excluded from supported flow. The
  only broad mechanism exceptions are graphics and sound backends, which may
  replace hardware after their logical contracts are recovered without
  changing input-driven state or ordering.
- **DOS timing and game-flow cadence are mandatory.** Preserve the recovered
  DOS timing contract wherever it affects input sampling, scheduler callbacks,
  animation, audio, frame publication, races or state. Do not assume 60 Hz from
  a browser or display; recover the executable's PIT/`INT 8`, timer-slot,
  VBL/wait and runtime-period evidence from DOS. Browser and Falcon simulation
  must use an explicit deterministic tick/event scheduler, while
  `requestAnimationFrame`, host timers and physical VBL may drive presentation
  only. They may not define simulation order or drop, duplicate, accelerate or
  delay authoritative ticks. Preserve drift-free accumulators and input
  poll/acknowledgement position where proven. An unrecovered cadence is
  `Unproven`; a fixture cadence is a labelled harness/presentation artefact,
  not DOS parity. A 60 Hz Falcon presentation target is a display choice, not
  permission to alter DOS game flow. Record every timing substitution and
  measured difference in the function ledger.
- **A runnable fixture must expose its evidence seam.** If a browser slice is
  driven by a fixture cadence while DOS wall-clock timing is `Unproven`, keep
  the logical `advanceTicks(count)` entry point independent of presentation and
  label the host clock as a harness artefact. Retain ordered replay/input bytes,
  emitted events, pre-draw/post-tick state checkpoints, and canonical logical
  framebuffer/page hashes in a bounded trace that regression fixtures can read.
  Do not attach a DOM key or button directly to game state: an unrecovered DOS
  input path stays `Unproven`, and any restart/pause convenience control is
  visibly marked as a harness control excluded from supported flow.
- **Function-body translation must not add defensive behaviour.** A JavaScript
  counterpart reproduces the recovered DOS function and side effects directly;
  it must not add `throw` paths, assertions, validation, clamps, defaults,
  retries or logging branches that the DOS function does not have. Preserve
  fall-through, return values, widths, wrapping, side effects, ordering and
  unsupported-input behaviour; mark an unrepresentable case `Unproven` or
  `Unsupported` instead of improving it. Assertions, hashes, diagnostics and
  failure reports belong in build/fixture/parity harnesses or necessary host
  and target boundaries, outside the semantic function path. A boundary guard
  required to prevent a host crash is a documented target artefact, never
  invented DOS error handling.
- **Browser file access goes through a virtual DOS filesystem.** The semantic
  core uses deterministic named-byte-file `open`/`read`/`seek`/`tell`/`close`
  semantics. IndexedDB may persist imported binaries, caches and saves;
  `localStorage` is metadata-only; fetch/file-picker APIs are host import
  adapters and never semantic dependencies. Cache hits and fresh imports must
  expose the same bytes, hashes, paths, positions and errors.
- **Two things that are also invention**, and neither looks like it while you
  are writing it. *A guard the original does not have* — a clamp or range
  check added for safety is a second behaviour for input nobody has checked
  against the first, and it hides which one is wrong; it belongs only where a
  genuine platform boundary forces it, documented beside what the original
  does. *Tuning code to close a gap against a measurement you doubt* — fitting
  to a bad oracle destroys traceability more thoroughly than a guessed
  constant, because the result matches and nobody looks again. Both are worked
  examples in METHOD.md §4.2, from CMN 2026-08-22: three guards written and
  removed the same day, and a terrain silhouette that stayed 21-23 rows off
  through eight parameter fits because no scalar in a projection can change
  the shape of a profile.
- **Rank the citation, because a citation is only as strong as the
  disassembly behind it.** An address in a region nobody proved was code is a
  guess wearing ground truth's clothes, and Ghidra returns a plausible
  `FUN_xxx+0y` for any address you ask about. Four evidence ranks, named in the function record:
  header: **executed** under telemetry (§6) is strongest, **covered by the
  reassembly ratchet** (§4a) is strong, **reached only by a sweep's
  inference** (§1) is weakest and says so, and a **recovered source tree** is a
  fourth kind of supporting evidence that has to declare *which build* it
  reconstructs and *what its fidelity grade is* before it can be cited at all.
  Porting from a weak rank is allowed; presenting it as a strong one is not.
- **Behaviour is not build-selectable** (CMN's rule). A flag that selects
  between two candidate behaviours is a decision that has not been made, and it
  hides the one that is wrong. Recover the original's behaviour, implement it,
  delete the alternative; if two readings of the listing are both plausible,
  the answer is more disassembly, not a flag. Flags that choose *which machine*
  does the work — CPU vs. DSP — are a different thing and are fine.
- **Put the target seam at the narrowest observable logical representation**:
  indexed pixels plus palette for POR, or the equivalent logical pixels,
  events or actions for another game. Keep common code target-neutral and
  assemble for the lowest supported CPU. Converters decode DOS records field
  by field and emit big-endian, explicitly aligned output — never
  memcpy-and-byteswap — while the decoded DOS layout remains unchanged.
- **Verify at equality-capable checkpoints, not by eye alone**: compare decoder
  output, state, framebuffer regions or other declared fixtures and retain
  hashes as regressions. Visual inspection is useful only beside numeric or
  byte-level evidence.

F29 is the family's working example of the delivery side — numbered task
slices that each ship a rendered frame, integration points named by symbol,
self-checking placeholders, measured rather than calculated performance — see
its `docs/ENGINE.md` / `HUD.md` / `MENU.md` and METHOD.md §4.6–4.7.

## What to adopt here (F29)

F29 is the source of most of §1–§5 and needs the least methodologically. What
it can take from the siblings is harnesses — and, now that its port is the
family's furthest along, the phase-4 policies written down in METHOD.md §4.

1. **Run the reassembly ratchet on `X.EXE`** (§4a; METHOD.md §2.4). nasm is
   already installed and the 68 KB binary is the family's smallest target. The
   ratchet is the *positive* invariant next to the data guard's negative one:
   it mechanically locates every jump-into-mid-instruction site, turns the 132
